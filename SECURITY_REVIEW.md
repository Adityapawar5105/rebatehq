## Assets and trust boundaries

1. Untrusted files → worker parsers/staging → explicit review → local DuckDB.
   Prices, costs, invoices, rules, simulations and margins stay in this flow.
   SQL is generated by worker code; the UI protocol accepts named operations,
   not SQL. Money is fixed decimal or integer cents, sent as strings.
2. Passphrase → worker WebCrypto → encrypted OPFS generations and encrypted
   folder/file backups. Working and staging databases use RAM, including the
   RAM-only wrapper whose compatibility path happens to start with `opfs://`.
   A passphrase is not a Supabase credential. There is no recovery escrow.
3. Browser → same-origin Next.js → Supabase Auth/restricted Postgres connection:
   identity, membership, invitations, licence/seat/location/device metadata.
   Control metadata includes personal information (email, IDs and IP-related
   authentication records); it is not anonymous. No user-facing service key.
4. Deployment/package supply chain → first-party JS, pinned DuckDB-Wasm 1.32.0,
   self-hosted worker/WASM. Runtime integrity pins protect separate engine assets;
   the HTTPS origin, app code, embedded pins and build chain remain trusted.
5. User-selected export/backup destination → operating system and other users.
   A chosen CSV/XLSX/PDF report is a plaintext business export. Only `.enc` vault
   backups have vault encryption; ordinary reports must be protected separately.
6. Future relay → hostile storage/network; payload keys must remain at endpoints.
   There is no live relay to test or claim secure in this chunk.

Assume a supported, updated Chrome/Edge and uncompromised OS/origin. A hostile
extension, local administrator, an unlocked-device attacker or injected same-origin
JavaScript can read unlocked data. UI roles hide fields in the worker but do not
cryptographically separate people who possess the same complete vault/passphrase.

service, E = elevation of privilege. Evidence names refer to checked-in tests;
passing baseline evidence is [CI #73](https://github.com/Adityapawar5105/rebatehq/actions/runs/41977200715)
and [local Restore #18](https://github.com/Adityapawar5105/rebatehq/actions/runs/41979671868).

## 7A relay review addendum — 5 November 2026

Design was written before code in RELAY_DESIGN.md. New tables contain only
cryptographic material and routing metadata. Server SQL uses the restricted app
role with signed request context. Public verification is allowed server-side;
no private device key, passphrase, workspace key or plaintext content is accepted.
The app's standard flow encrypts in the worker before any network send. A hostile
client/keyholder can submit arbitrary bytes; opaque storage alone cannot prove
that an intentionally malicious client encrypted them. The fixture privacy gate
proves the tested normal flow, not resistance to a compromised trusted client.

New reviewed controls: manual fingerprint confirmation (no silent TOFU), separate
ECDH/ECDSA keys, ephemeral HKDF/GCM key wraps, per-message HKDF subkeys/random IVs,
canonical signed headers, low-S signature validation, global signed chain and
signed rotation base, durable encrypted outbox/idempotency, strict body schemas,
metadata-only DB audit, append-only app ACLs and bounded quotas. Any signed but
invalid/undecryptable content is visibly quarantined after signature validation;
it never grants approval. A bad signature or missing/reordered history stops sync.

| ID | Severity / state | Finding / action | Owner / review |
|---|---|---|---|
| R11 | Medium, accepted limit | A malicious relay can hide an unseen tail or maintain forks for isolated devices. Compare verification heads through an independent channel. No external transparency service or unconditional completeness claim | Aditya Pawar / 2026-11-19 |
| R12 | Medium, open | Independent cryptography/protocol review, hosted configuration and operational recovery have not happened. Keep operator flag off until the review/CI/restore gates are satisfied | Aditya Pawar + reviewer / before production enablement |
| R13 | Medium, accepted limit | All approved workspace relay members share the epoch key. Removal needs rotation; old ciphertext/keys cannot be erased. Losing all trusted admin devices/backups makes sharing unrecoverable | Workspace owner / onboarding and each removal |
| R14 | Low, open | Manual sync only; no email/push, retention pruning or subgroup keys. Workspace quota exhaustion requires an operator-managed reviewed recovery/export procedure | Aditya Pawar / before broad deployment |
| R15 | Medium, fixed (CI pending) | The CSRF origin check in `proxy.ts` compared a write request's `Origin` with `request.nextUrl.origin`, which reflects the address the server is bound to. ## Recovery and device onboarding addendum — 20 November 2026

First-party review of the recovery features added for audit B-3 and B-5 (roadmap Phase 5). Not independent assurance.

**Start again on this device (`vaultReset`).**
- Runs only while the vault is locked. It takes the same Web Lock lease as unlock, so it cannot run while the vault is open in another tab.
- It deletes the files in this workspace-and-user vault folder only. Other people's vaults and other workspaces on the device are separate folders.
- The UI asks the person to type the workspace name. That is a guard against slips, not authentication: anyone at an unlocked browser profile could already delete site data from the browser settings.
- It needs no licence: it only removes local files, and a lapsed licence must not block recovery.

**Change passphrase (`passphraseChange`).**
- The current passphrase is checked by decrypting the saved snapshot. A new 16-byte salt is drawn, and the vault is saved under the new key.
- All older snapshots and `head.previous.json` are then removed, so the old passphrase opens nothing on this device.
- The old passphrase still opens any backup made before the change, and the screen says so.
- If removing the older copies fails, the person is told to finish the change. Until then an older copy under the old passphrase may remain.
- The passphrase fields are cleared from the page as soon as they are sent.

**Device list (`GET /api/licence/devices`).**
- The workspace Owner now sees each device's member email, from `membership`, which the Owner can already read on the Users page.
- Other members get no emails.
- The response says whether the caller can approve devices, and the vault shows a badge to the Owner while one is waiting.

| ID | Severity / state | Finding / action | Owner / review |
|---|---|---|---|
| R16 | Low, accepted | A passphrase change cannot reach backups already exported or written to a backup folder; they keep the old passphrase. This is stated on screen. Rotating a compromised passphrase also needs those backups replaced | Aditya Pawar / with R02 |
| R17 | Low, open | If removing the older snapshots after a passphrase change fails part-way, an older snapshot under the old passphrase can remain until the change is repeated. The error says so. Consider an automatic retry on the next unlock | Aditya Pawar / next recovery change |

**Privacy gate allow-list (20 November 2026).** While the vault is open, the page may now also call `GET /api/licence/devices` (no query, no body), for the Owner's "devices waiting" badge. It is control-plane metadata: device ids, statuses, dates and, for the Owner only, member emails. Every request's URL, headers and body are still scanned for the private markers. This is the only addition to `GET /api/licence?device=…`.

## Team sharing S2–S5 addendum — 26 November 2026 (review R2)

**Scope.** This addendum covers the attack surface team sharing added after the 7A review:
- format 2 epochs with the signed grid and per-pack keys (S2);
- encrypted pack chunks in the private Supabase Storage bucket `relay-packs`, and the rule `rebatehq_storage.relay_storage_allowed` (S3);
- `/api/relay?mode=token`, which hands the signed-in person's own session token to the vault worker so it can reach Storage and Realtime directly (S3, S4);
- the Realtime doorbell, a private channel per pack with `rebatehq_storage.relay_channel_allowed` (S4);
- small deltas (S4b);
- threads, tasks and the inbox, sealed under pack keys (S5).

**Method.** It comes from the 26 November full project review: six reviewers who had no project history read the code, and the findings were checked against it. It is not an independent review. R02, R09 and R12 still apply, and sharing stays behind `RELAY_ENABLED` until those are met.

### Application table ACL finding from Restore Drill #4

Restore Drill #4 exposed a real ACL difference: source application tables had a direct `anon` DELETE grant and `service_role` grants including INSERT, MAINTAIN, REFERENCES, SELECT, and TRIGGER (reported grantor `postgres`); those grants were absent on the restored target. `service_role` bypasses RLS, and the user-facing service-role scan finds no application path that uses it, so its application-table allowlist is intentionally empty. New migration [`202610250001_revoke_platform_public_privileges.sql`](./supabase/migrations/202610250001_revoke_platform_public_privileges.sql) revokes table and column privileges from `anon`, `authenticated`, `service_role`, and `PUBLIC` on every application tenant table. It also removes matching default ACL entries for the roles that own application objects, including public tables, sequences, and functions. It leaves the previously verified explicit `margindesk_app` grants intact. `migrations.lock` now records this normalized hash as applied/locked. Clean migration application and the strict ACL comparison passed in CI #24 and Restore Drill #8; the lock checker also passes locally after promotion. The restore comparison now prints every table owner and full source/restored ACL, both databases' global and `public` default ACL entries, and a complete ACL diff grouped by grantee before enforcing strict equality. The cleanup, explicit allowlists, and source/target comparison passed in [MarginDesk CI #24](https://github.com/Adityapawar5105/rebatehq/actions/runs/40290388651/job/121463801598) and [MarginDesk Restore Drill #8](https://github.com/Adityapawar5105/rebatehq/actions/runs/40291362616/job/121466953508), 2026-10-26.

### Public function ACL finding from Restore Drill #5

Run #5 passed the table ACL comparison, then found Supabase-default EXECUTE grants to `anon`, `authenticated`, and `service_role` (grantor `postgres`) on public application functions, including SECURITY DEFINER functions, in the source. The affected grants were absent from the restored target. This meant browser roles could invoke privileged function entry points through Supabase's default public grants. The new function ACL migration applies only to functions owned by the migration role; it removes all non-owner grants except the explicit per-function `margindesk_app` allowlist, leaves Supabase-owned functions untouched, and clears future public function EXECUTE defaults for application object owners. The test suite now asserts the exact grantee set for every migration-role-owned public function, checks SECURITY DEFINER ownership and pinned `search_path`, and calls each app-exposed function as both `anon` and `authenticated`, requiring SQLSTATE `42501` with `permission denied for function`. Restore snapshots now include every public function (SECURITY DEFINER and INVOKER), function arguments, owner, security type, search path, and complete ACL. On function-section failures, the workflow logs both full inventories and a strict diff grouped by function and grantee. The migration is locked as applied in `migrations.lock`; the exact function ACL allowlist and SECURITY DEFINER checks passed in [MarginDesk CI #24](https://github.com/Adityapawar5105/rebatehq/actions/runs/40290388651/job/121463801598) and [MarginDesk Restore Drill #8](https://github.com/Adityapawar5105/rebatehq/actions/runs/40291362616/job/121466953508), 2026-10-26.

## 1. Connection role and RLS context

### Which role does the app pool use?

`APP_DATABASE_URL` is the PostgreSQL login used by the `pg.Pool` in [`lib/db.ts`](./lib/db.ts). The login must be a dedicated non-superuser role that is a member of `margindesk_app`. Each request transaction then runs `SET LOCAL ROLE margindesk_app`, so SQL statements execute under that restricted role while `session_user` continues to identify the login used by the pool. Separately, `scripts/test-db.ts` connects with `TEST_DATABASE_URL`; CI sets it from the disposable local Supabase `DB_URL`. The setup script grants this test login membership in `margindesk_app` only on the disposable test database, using `WITH INHERIT FALSE, SET TRUE` on PostgreSQL 16+ (the Supabase config currently selects PostgreSQL 17). It logs the live server major version and test-login `LOGIN`, `SUPERUSER`, and `BYPASSRLS` attributes without logging connection credentials. Runtime role and membership checks passed in CI run [MarginDesk CI #24](https://github.com/Adityapawar5105/rebatehq/actions/runs/40290388651/job/121463801598), 2026-10-26.

The migration creates `margindesk_app` as `NOLOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS`. CI run [MarginDesk CI #24](https://github.com/Adityapawar5105/rebatehq/actions/runs/40290388651/job/121463801598), 2026-10-26 verified the role attributes, runtime login membership, and captured effective role flags. The pgTAP suite captures `current_user`, `rolsuper`, and `rolbypassrls` while `margindesk_app` is active, then checks those values after `RESET ROLE`. It does not grant the app role access to the pgTAP extension schema or temporary fixture tables.

Evidence command to run over the same connection string configured as `APP_DATABASE_URL`:

```sql
BEGIN;
SET LOCAL ROLE rebatehq_app;
SELECT session_user AS pool_login, current_user AS effective_role,
       login.rolsuper AS login_is_superuser,
       login.rolbypassrls AS login_bypasses_rls,
```

### How is the authenticated request context applied?

[`lib/db.ts`](./lib/db.ts) performs these operations in one transaction, in order:

1. `BEGIN`.
2. Validate the PostgreSQL login role flags and membership.
3. `SET LOCAL ROLE rebatehq_app`.
4. Set transaction-local `request.jwt.claim.sub`, `request.jwt.claim.role`, and `request.jwt.claims` from the user ID returned by Supabase Auth’s verified `getUser()` call. The claims are cleared at transaction end.
5. Set `app.real_actor_id`, client IP, and user agent for audit triggers.
6. Run the tenant query and commit; errors roll the transaction back.

RLS helpers use auth.uid() and active membership checks. CI run [MarginDesk CI #24](https://github.com/Adityapawar5105/rebatehq/actions/runs/40290388651/job/121463801598), 2026-10-26 passed both the runtime check that clears request context and the pgTAP controls that return zero tenant rows without authenticated claims.

### Auth privilege decision

The application-code search found no direct SQL call to `auth.*` through the app pool, server library, or API routes. `scripts/seed-demo.ts` reads `auth.users` only through its `SEED_DATABASE_URL` administrative pool; its application import runs separately through `withDatabase`. Calls such as `supabase.auth.getUser()` use the Supabase Auth client and are not SQL access to the `auth` schema. Therefore the app role does **not** receive `USAGE` on schema `auth`; check 6 asserts its absence and check 7 asserts it has no Auth-table privileges.

Stored RLS expressions reference `auth.uid()`, but PostgreSQL evaluates their stored function reference without requiring schema USAGE at query time. The app role has no direct ACL entry or role membership for this function. The reported PostgreSQL 17 catalog evidence identifies the effective permission path as Supabase PUBLIC EXECUTE, owned and granted by `supabase_auth_admin`; the migration role cannot alter that ACL. The migration now makes no auth-schema/function GRANT or REVOKE attempt. Check 9 requires effective EXECUTE plus a PUBLIC ACL entry, and its logged owner/ACL make a platform change visible. ## 2. Tenant isolation across public tables
